## 1. 問題現況

管理後台目前處理「同場地同時段衝突」的流程在 [`BookingsTab.tsx`](../frontend/src/pages/admin/BookingsTab.tsx)：

- 「⚠️ 有衝突」子分頁把衝突預約**用列表逐筆列出**（`overlapMap` 計算，第 312–392 行）。
- 每筆衝突卡片會展開一段紅色區塊，列出「與哪幾筆重疊、借用人、時間、狀態」。
- 要把某筆移到別的場地，得點「📍 變更場地」開一個 **下拉選單 Modal**（`assigningBooking`，第 1356–1388 行），從清單挑一個場地。

痛點（使用者原話）：

1. **「有衝突用成列表很難觀察跟調整」** — 列表看不出「同一天、同一時段、其他場地是不是空的」。
2. **「需要看借用概況才會知道衝突後可以把它移到哪個其他場地」** — 判斷要搬去哪，得先看週看板（借用概況），但那是另一個分頁。
3. **下拉選單挑場地**沒有「哪些場地在這個時段是空的」的視覺提示，容易挑到又撞的場地（送出後才被後端 409 擋下）。

## 2. 目標與非目標

### 目標

- 在**一個畫面**同時看到「借用概況（週/日看板）」＋「目前有哪些衝突」。
- **待審核**的預約卡片可以**用滑鼠像積木一樣拖曳**，直接放到另一個場地的欄位格。
- 放下的瞬間就能看出目標格**是空的還是又會撞**（拖曳中即時提示）。
- 一次調整只送一個「改場地」請求，**不改借用人選的日期與時間**。
- 已核可的預約可一鍵「**退回待審核**」，退回後即可拖。

### 非目標（這次不做）

- 不調整預約的**日期 / 開始 / 結束時間**（維持使用者原本借的時段）。
- 不做手機版拖曳（後台手機走既有的 [`MobileAdminDashboard`](../frontend/src/components/MobileAdminDashboard.tsx) 流程，維持不變）。
- 不改「核可 / 拒絕」的既有審核按鈕邏輯；拖曳只改 `room_id`，另新增一個「退回待審核」動作。
- 拖曳搬場地**不改變狀態**、**不寫 log**。
- 不自動幫忙選場地（Phase 3 再考慮「建議空場地」）。
- 週檢視（Phase 2）。

## 4. 使用者流程

1. 後台 →「預約申請審核」→「⚠️ 有衝突」子分頁。
2. 分頁右上新增按鈕 **「🧩 拖曳調整看板」**。點下去開一個全螢幕遮罩（overlay）。
3. 看板預設打開**「衝突最多的那一天」的日檢視**（或使用者當下選的日期）。頂部可切換前後日期。
4. 看板 = 借用概況同款網格：左側時段列、上方場地欄。所有預約都畫成塊（提供上下文）：
   - **待審核（pending）塊**：可拖，`cursor: grab`；有衝突者再加紅色脈動外框 + 小標「拖我到空位」。
   - **已核可（approved）塊**：不可拖（固定錨點），右上角有一顆小按鈕 **「↩ 退回待審核」**。
5. 若衝突雙方都是已核可、或要動的那筆是已核可 → 管理員先點該塊的「↩ 退回待審核」：
   - 送 `apiUpdateBookingStatus(id, 'pending')` → 成功後該塊變成可拖狀態。
   - 若該筆原本已發門鎖密碼，一併清空並提示「已清除原門鎖密碼」。
6. 管理員**按住一個待審核塊拖曳**：
   - 拖曳中，網格裡**該時段所有場地格**即時上色：綠底＝可放（該場地此時段沒有 approved / pending 的重疊預約）、灰斜線＝不可放（會再撞 / 是虛擬場地 / 是自己原本的格）。
   - 塊本身時間不變，只是換欄。
7. 放到綠色格 → 樂觀更新（塊立刻移過去、衝突外框消失）→ 背景送 `apiAssignBookingRoom(id, 新room_id)`。
   - 成功：跳一個輕量 toast「已將『XXX』改到『會議室B』」，並 `onRefresh()` 重抓。狀態**維持 pending**。
   - 失敗（網路錯 / 後端拒絕）：塊**彈回原位**，紅色 toast 顯示後端訊息。
8. 衝突清完，關掉遮罩回到列表。之後管理員再依常規逐一「核可」。

  - **主體**：可捲動網格（沿用 `WeeklyBulletin` 的 sticky 表頭 + sticky 左欄 + `zoom` 縮放）。
  - **底列（選配）**：圖例（綠＝可放、灰斜線＝不可放、紅框＝衝突、鎖＝已核可需先退回）。

### 預約塊（卡片）

沿用 `renderBookingCard`（`WeeklyBulletin` 第 322–431 行）外觀，依狀態分：

| 狀態 | 可否拖 | 視覺 |
|---|---|---|
| 待審核、未過期、非衝突 | ✅ | 琥珀色，`cursor: grab` |
| 待審核、未過期、有衝突 | ✅ | 琥珀色 + 紅色脈動外框 + 角標「⚠️」；hover 顯示「拖我到空位」 |
| 已核可、未過期 | ❌（要先退回） | 綠色 + 🔒；右上角小按鈕「↩ 退回待審核」 |
| 拖曳中 | — | 半透明（`opacity-40`）、輕微放大、跟隨游標的殘影 |
| 已過期 | ❌ | 灰階（比照 `isBookingPast`），無「退回」按鈕 |

### 落點格（drag over 提示）

拖曳開始時，只有**與被拖塊同一天、同一時段列**的場地格會進入「候選」狀態：

- **可放（綠）**：`bg-emerald-50 ring-2 ring-emerald-400`，游標 `copy`。
- **不可放（灰斜線）**：`bg-[repeating-linear-gradient(...)] opacity-60`，游標 `not-allowed`。理由：
  - 目標場地此時段已有 `approved` 或 `pending` 的重疊預約；
  - 目標是被拖塊**原本的場地**（無意義）；
  - 目標是虛擬場地「💒 由教會分配」；
  - 目標是父/子場地，而其對應父或子已被佔用（沿用 `check-all` 的父子擴張）。
- 其他時段的格**不反白**，避免畫面雜訊。

## 6. 落點規則（前端即時判定）

抽一個共用函式，日檢視內對「被拖預約 `b` + 候選場地 `roomId`」判斷：

```
canDrag(b):
  b.status === 'pending' && 未過期        // 已核可要先「退回待審核」

canDrop(b, roomId, allBookingsSameDay, rooms):
  if !canDrag(b)                     -> false
  if roomId === b.room_id            -> false（原地）
  if room(roomId).name 含「由教會分配」 -> false
  相關場地集合 = { roomId } ∪ 父(roomId) ∪ 子(roomId)     // 同 check-all
  對 allBookingsSameDay 中 status ∈ {approved, pending} 且 id ≠ b.id：
     若 其 room_id ∈ 相關場地集合
        且 時間重疊(其, b)   // b.start < 其.end && b.end > 其.start
        -> false
  -> true
```

- **時間比對**用字串比較即可（格式 `HH:MM:SS`，與現有 `overlapMap`、`checkOverlap` 一致）。
- 因為只拖 pending，後端 `PUT /bookings/:id/room` **不會**跑 `checkOverlap`（那段只在 approved 時執行）。也就是說落點正確性**完全由前端 `canDrop` 把關**。
- 可接受的理由：pending 本來就還沒定案，就算兩個 admin 同時搬造成新的 pending 疊 pending，也只是「又出現一個待處理衝突」，看板會再標出來，不會破壞已核可的排程。
- 若仍想要伺服器端保險，見 §7「可選的後端補強」。

## 7. 技術實作方案

### 建議：原生 HTML5 Drag and Drop（不加依賴）

- 塊：`draggable`，`onDragStart` 把 `booking.id` 塞進 `dataTransfer` + 存進 `draggingId` state。
- 格：`onDragOver`（`preventDefault` 才能 drop）依 `canDrop` 決定 `dropEffect` 與樣式、`onDrop` 執行搬移、`onDragLeave` 清狀態。
- `onDragEnd` 一律清 `draggingId`。
- 優點：零依賴、桌機支援完整（後台桌機為主）。
- 缺點：拖曳殘影樣式較難客製、行動裝置支援差 → 本案行動裝置本就不做拖曳，可接受。
- 備案：`framer-motion` 的 `drag` + `onDragEnd` 命中測試（`document.elementFromPoint`）。客製度高但要自己算落點，複雜度較高，非必要不採用。

### 元件與資料

- 新元件 `frontend/src/pages/admin/ConflictBoard.tsx`：
  - props：`bookings: Booking[]`（用 `apiFetchAdminBookings` 的**未遮罩**資料，`AdminPanel` 已在抓）、`getToken`、`onClose`、`onRefresh`、`initialDate`。
  - 內部抽用 `WeeklyBulletin` 的網格建構邏輯（父子分組 → `leafColumns` → 時段分列）。**建議先把那段抽成 `frontend/src/lib/roomGrid.ts` 共用**，`WeeklyBulletin` 與 `ConflictBoard` 都引用，避免複製貼上。
  - 衝突判定抽成 `frontend/src/lib/bookingConflicts.ts`（從 `BookingsTab` 的 `overlapMap` 搬過來），`BookingsTab` 也改用它。
- `BookingsTab` 的「有衝突」子分頁加一顆按鈕 `setBoardOpen(true)` 開 `ConflictBoard`。
- **退回待審核**處理：

```
onRevertToPending(booking):
  if (!confirm(`確定將「${name}」退回待審核？若已發門鎖密碼會一併清除。`)) return
  const res = await apiUpdateBookingStatus(token, booking.id, 'pending')
  if (res.ok) { toast(綠, '已退回待審核，現在可拖曳'); onRefresh() }
  else { toast(紅, err.error) }
```

- 落下處理：

```
onDrop(targetRoomId):
  1. 記 prev = booking.room_id
  2. setLocalBookings 樂觀更新該筆 room_id = targetRoomId
  3. const res = await apiAssignBookingRoom(token, booking.id, targetRoomId)
  4. if (!res.ok) { 還原 room_id = prev; toast(紅, err.error) }
     else { toast(綠, `已將「${name}」改到「${roomName}」`); onRefresh() }
```

- Toast：可用現有 [`StatusToast`](../frontend/src/components/StatusToast.tsx) 或簡單自製；**不要用 `alert()`**（拖曳流程被 modal 打斷體驗差）。`confirm()` 僅用於「退回待審核」這種一次性動作，可接受。

### 後端改動（Phase 1 必要）

**1. `PUT /bookings/:id/status` 要能接受 `'pending'`（[`admin.js:102`](../backend/routes/admin.js:102)）**

現況第 106 行 `if (!['approved', 'rejected'].includes(status))` 直接擋掉 `pending`。需：

- 白名單加入 `'pending'`。
- `status === 'pending'` 時：不跑 `checkOverlap`（本來就是要進待審核池）、**不寫任何 violation log**、清掉 `access_code` 與 `tuya_password_id`（若原本 approved 已發碼，並呼叫 `deleteLockPasscode` 收回實體鎖碼，比照 reject 的第 135–142 行）、清 `rejection_reason`。
- 權限維持 `requireRole(['admin', 'system_admin'])` 與現有據點檢查。

**2. `apiAssignBookingRoom` / `PUT /bookings/:id/room` 不用改**

只改 `room_id`；對 pending 不跑衝突檢查（符合本案）；不呼叫 `logChangeViolation` —— 管理員為解衝突搬場地，不該記在借用人頭上。

### 可選的後端補強（非 Phase 1）

若要伺服器端也擋「pending 拖到已被佔用的格」：在 `PUT /bookings/:id/room` 把 `checkOverlap` 的條件從「僅 approved」放寬 —— 但 `checkOverlap` 目前只查 `status = 'approved'` 的對手，需另外加一個「查 pending 對手」的版本，且要決定「pending 撞 pending 要不要擋」。因需求方已接受前端把關，這塊列為 backlog。

## 8. 邊界情況

| 情況 | 處理 |
|---|---|
| 衝突雙方都是已核可 | 兩塊都不可拖 → 管理員先對其中一塊點「↩ 退回待審核」，再拖 |
| 要動的那筆是已核可、對手是待審核 | 對已核可那筆點「退回待審核」後才可拖；或直接拖對手那筆待審核 |
| 被拖（pending）預約是父場地，目標是獨立場地 | 允許，`room_id` 直接改成目標；原父場地格空出 |
| 目標是子場地，父場地同時段有人 | `canDrop` = false（灰斜線） |
| 「退回待審核」的那筆原本已發門鎖密碼 | 後端清 `access_code` / `tuya_password_id` 並收回實體鎖碼；toast 提示「已清除原門鎖密碼」 |
| 拖曳中其他管理員剛好也改了同一格 | 前端提示綠燈但實際已被佔 → `onRefresh` 後看板重算，會再標成衝突讓管理員處理 |
| 「💒 由教會分配」虛擬場地 | 永遠不可作為落點；其上的（pending）預約可被拖出去（就是要指派實體場地） |
| 過去日期 / 已結束時段 | 塊不可拖、無「退回」按鈕；格不亮綠 |
| 一個時段列有多筆 pending（本來就疊在同格） | 每筆各自可拖；拖走一筆後其餘重算衝突外框 |
| 拖到沒有預約的空格 | 正常，`canDrop` = true |
